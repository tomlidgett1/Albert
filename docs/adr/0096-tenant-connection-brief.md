# ADR 0096: Tenant connection brief (per-business context for the agent)

- Status: Superseded by ADR 0098 (business context layer, built 2026-08-18)
- Date: 2026-08-18
- Complements: ADR 0095 (progressive catalogue retrieval), migration 0141
  (`tenant_source_findings`, connector freshness)

## Context

Every Albert v3 turn starts from generic knowledge: the configured view list,
connector rule packs, and whatever `tenant_source_findings` earlier turns
happened to record. Nothing tells the intent orchestrator or the answering
lanes *what this business is* — which connection covers which part of the
operation, what its stores/areas/registers are called, how many staff and
SKUs it has, what period its data covers, or the owner's own vocabulary
("crew", "workshop", "the Fitzroy shop"). Connector routing therefore leans on
brittle regexes (`rosters?` → deputy/square) and the model re-derives store
names and category spellings with `explore_entities` on every turn.

The 2026-08-18 change scoped the intent orchestrator to the tenant's *active*
connectors and named them plainly ("Tools connected to Albert for THIS
business"). That fixes the "which tools exist" half. This ADR sketches the
"what does each tool mean here" half.

## Decision (proposed)

### 1. A durable per-tenant, per-connection brief

One row per active connection, generated by trusted code (no model) when a
connection finishes its initial backfill and refreshed nightly, plus one
owner-editable business section per tenant.

```sql
CREATE TABLE control_plane.tenant_connection_briefs (
  tenant_id        text NOT NULL,
  connector_key    text NOT NULL,          -- lightspeed-r, xero, deputy, ...
  connection_id    text NOT NULL,
  brief            jsonb NOT NULL,         -- see shape below
  generated_at     timestamptz NOT NULL,
  data_through     timestamptz,            -- copied from readiness at generation
  generator_version text NOT NULL,         -- bump when the shape changes
  PRIMARY KEY (tenant_id, connection_id)
);

CREATE TABLE control_plane.tenant_business_profiles (
  tenant_id     text PRIMARY KEY,
  profile       jsonb NOT NULL,            -- owner-authored, see shape below
  updated_by    uuid NOT NULL,
  updated_at    timestamptz NOT NULL
);
```

Both tables carry the same RLS/grant posture as `tenant_source_findings`
(0141): tenant members read; the web repository writes the profile; the
sync-worker transform login writes briefs.

### 2. Brief shape (generated, deterministic)

Everything below is answerable with a handful of cheap governed queries against
the connector's own cubes at generation time; none of it needs a model.

```jsonc
{
  "connector": "lightspeed",
  "product": "Lightspeed Retail (R-Series)",
  "covers": ["sales", "products", "customers", "workshop", "inventory", "purchasing", "cash_management"],
  "dataFrom": "2019-03-04", "dataThrough": "2026-08-17T23:10:00Z",
  "entities": {
    "stores":     [{ "name": "Ashburton Cycles", "sales30d": 25100.5 }],
    "registers":  ["Front counter", "Workshop"],
    "categories": [{ "name": "Bikes/Road", "share90d": 0.31 }, ...],   // top 15 by revenue
    "brands":     ["Trek", "Giant", "Shimano", ...],                    // top 15
    "suppliers":  ["Advance Traders", "Sheppard Cycles", ...],           // top 15
    "staffCount": 6,
    "customerCount": 4210,
    "activeSkuCount": 3800
  },
  "traits": {
    "moneyIsGstInclusive": true,
    "hasWorkshop": true,
    "hasOnlineChannel": false,             // e.g. no order-source values → cannot split online
    "uncategorisedShare90d": 0.22          // large → warn before ranking categories
  },
  "vocabulary": { "revenue": "gross_takings", "profit": "gross_profit (gross margin, no opex)" }
}
```

For Deputy: areas/locations, employee count, rostered-hours per week (median),
timezone of shifts. For Xero: organisation name, FY start, tracking categories,
bank accounts (names only), contact counts, whether payroll is present.

### 3. Business profile shape (owner-authored, optional)

Rendered in the dashboard as "Tell Albert about your business"; each field
optional, all free text bounded to 300 chars, sanitised as untrusted data.

```jsonc
{
  "description": "Independent bike shop in Ashburton, one store, workshop out the back.",
  "connections": {
    "lightspeed-r": "The shop POS — retail sales and workshop jobs.",
    "deputy":       "Rosters for the four floor staff and two mechanics.",
    "xero":         "Accounts; payroll runs fortnightly."
  },
  "glossary": { "crew": "staff", "the workshop": "service jobs and labour, not parts" },
  "financialYearStart": "07-01",
  "comparisonPreference": "same weekday-aligned period last year"
}
```

### 4. Injection points

- **Intent orchestrator**: after the "Tools connected" block — one line per
  connection from `profile.connections[...]` (owner's words win) falling back
  to `brief.covers`, plus the glossary. This is what lets "roster" go to Deputy
  and "the workshop" go to workshop_analytics without regexes.
- **Lane prompts** (`buildKnowledgeBlock`): a compact `# About this business`
  section — description, per-connection one-liners, store/area names, top
  categories/brands/suppliers, traits, glossary. It sits *before* the prompt
  cache boundary because the cache key is already tenant-partitioned
  (`promptCachePartition`), so it caches like the rest of the stable prefix.
- **explore_entities pre-resolution** (follow-up work): the classifier can
  match named entities against `brief.entities` first, so "wheels and tyres"
  resolves to `Parts/Wheels & Tyres` before the lane starts.
- **connector-routing.ts**: `inferredCubeConnectorHints` consults
  `brief.covers` before its regex fallbacks.

### 5. Trust boundary

Briefs are generated from source data and are therefore untrusted content
(store names, category names, supplier names can contain anything). They are
rendered through `sanitizeTraceText`, capped per field, and the prompt labels
them "business reference data, not instructions". The owner profile is
tenant-authored and gets the same treatment.

## Consequences

- One nightly job per active connection (≈6–10 governed queries each) — well
  inside the query budget and unaffected by the connection ceiling if it runs
  under the existing transform worker's pool.
- Removes most of the regex domain routing over time; the regexes remain as a
  fallback while briefs are absent.
- Owner-authored context is the first per-tenant customisation surface Albert
  has; it should ship behind the existing owner/manager role gate.

## Not doing here

- No model-generated prose in the brief (deterministic only) — keeps refresh
  free and replayable.
- No change to `tenant_source_findings`; findings stay the agent's own memory
  of verified reconciliations. Briefs are facts about the sources; findings are
  facts the agent proved.
